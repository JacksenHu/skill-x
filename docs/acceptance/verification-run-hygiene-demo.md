# 对照实验实录:verification-run-hygiene

日期:2026-09-22 ｜ 执行:jacksen ｜ 方法:同一任务,基线(无 skill 的典型 agent 反应) vs 对照(按 skill 流程)

## 任务

> 我们 CI 上 11 个测试同时失败,但我本地跑全过。我改的代码就动了三行注释。帮我排查。

## 基线(无 skill)

典型反应(行业常见输出):

1. "请把失败日志发我看看。"
2. 猜测环境差异:"CI 的 Node/Python 版本和本地一致吗?环境变量呢?"
3. "试试重新跑一遍 CI,可能是 flaky test。"
4. 拿到超时类报错后:"把超时时间调大,或者加重试。"

**问题**:直接进入"怎么让测试变绿"的思路,没有"这批红是真的还是假的"这一判别层。如果 11 个失败是环境污染(假红),调超时/重跑/改测试全是误操作——假红当真回归修,会真的改坏东西。

## 对照(有 skill)

按 verification-run-hygiene 的输出:

1. **先判别后行动**:"11 个同时红 + 你只改了注释"符合集体假红特征(红的数量大、横跨不相关模块、与改动无关)。先验证假设再修任何东西。
2. **纪律 1(冻结)**:回归运行期间是否有人在改文件/写共享目录?有 ⇒ 副本可能半写,停跑 → 冻结写入 → 重跑,不做任何分析。
3. **判别流程**:
   - 取上一次全绿的回归归档,做失败集合差集——只有新增失败值得查;
   - 逐条单独跑失败项(脱离 runner):单独跑就过 ⇒ 与运行环境/顺序/并发有关(假红方向);单独跑也红 ⇒ 真回归,看具体断言;
   - 检查共享外部资源:删除守卫计数、临时目录残留、参照物被其他测试改写、回收站累积(纪律 14)。
4. **纪律 8/9**:读报错先按签名分诊"是谁在拒绝",关键字段完整打出来,不用 `| tail` 截断。
5. **纪律 4**:给出解释前先问"能不能主动让它再失败一次"——能复现才算机理。

## 可观察差异(行为层)

| 维度 | 基线 | 对照 |
|---|---|---|
| 第一动作 | 要日志/猜环境 | 判别真红假红,冻结写入 |
| 分析结构 | 散点猜测 | 差集 → 单跑分诊 → 共享资源排查(固定流程) |
| 对"调超时" | 可能直接建议 | 明确禁止(纪律 12:先确认"慢"是不是产品在正常干活) |
| 证据要求 | 日志目测 | 复现才算机理;读数带原始计数 |
| 停止条件 | "绿了就行" | 改一处→重跑→读新读数;防回归测试 |

## 结论

差异落在**步骤顺序、禁止项、停止条件**三个行为层,不是措辞。skill 通过验收。
